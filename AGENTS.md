# Repository agent instructions

The game is called WOLF OVERRIDE, two words with no slashes, by Nathanial's decision (October 17, 2026). Write that name in code, game text, art, the website, docs and Notion; the old "WOLF//OVERRIDE" stays only as an alternative name for listings such as IGDB or inside quotes of history. The repository name `wolf-override`, the domain, URLs and file names do not change.

Read [AGENT.md](AGENT.md) before game, site or README work. It is the shared, public guide for playable quality, credits, asset provenance and honest test claims.

Read `PRIVATE_AGENTS.md`, `PROJECT_CONTEXT.md` and `docs/next-session.md` before story or gameplay changes; research, design notes, reviews and plans go to Notion through Codex, with the repo keeping rules, decisions, the manifest, credits and [docs/NOTES.md](docs/NOTES.md). They hold provisional story and design decisions and are tracked in this repository by Nathanial's decision (October 11, 2026), so they are public. Keep spoiler-heavy material out of the website, in-game text and build output. The latest explicit user decision wins.

Inspect Git status and task-relevant source before editing. Work in small, playable steps using the pinned Godot project at `apps/game`; keep the public site at `apps/docs`. WOLF is an independent companion, the engineer is the sole playable character, and essential progress needs an engineer-only fallback. Keep the original game and story credit with Nathanial Henniges.

Never open a Godot or game window on Nathanial's Mac while he works: run tests and checks with `godot --headless`, and make rendered captures with `tools/render/render.sh`, which renders inside a container (see `tools/render/README.md`). Run relevant checks and distinguish headless logic, rendered stills, hands-on play, exports and device tests. Do not claim a game-feel improvement was validated until the affected route was played. Preserve unrelated work and the populated asset register. Fetch connected pages before editing Notion or Jira; they do not sync with Git automatically.

Don't duplicate code. Before you write a script, scene, shader, test helper, style or tool, look for an existing one that does the job and use or extend it. When two places need the same logic, move it into one shared file that both use, and delete the copies in the same change. Jobs that run in parallel name their shared pieces first, so two branches don't each build their own. Reviews treat copied code as a defect, and nothing merges with new copies.

Keep a changelog as you go. Every pull request that changes the game, the site or the tools adds its one-line changes under **Next version (in development)** in `apps/docs/content/docs/changelog.mdx`, in the right group (Gameplay, Art, Audio, Accessibility, Settings, Website, Development), runs `python3 scripts/export_changelog.py` and commits the regenerated `apps/game/assets/changelog.txt` in the same pull request. A version is cut per milestone: rename Next version to `0.N.0 - <date>` with a one-line summary and one "How it was checked" line, set `application/config/version` in `apps/game/project.godot` to the same number (the single source of the version; the export fails when they differ), and start a new empty Next version. A cut version does not change afterwards.

Commit in small steps and push your branch to GitHub as you go, so no work exists only on one machine. Land finished work through a pull request; never push to main. Never add Co-Authored-By or other AI attribution lines to commits.

Give code good developer comments. Every script, class and non-obvious function gets a doc comment (`##` in GDScript) saying what it is for and its contract: inputs, outputs, units (world px, metres, seconds) and side effects. Constants say where their numbers come from, and comments explain why something is done, or why a simpler way doesn't work, rather than repeating the line. Update or delete a comment when its code changes; reviews check comments with the code.

Never search the whole disk or home folder (`find /`, `find ~`, `mdfind` or Spotlight) or open Finder windows to look for files or skills: on Nathanial's Mac that pops up access prompts while he works. Load a skill through your tool's skill loader or from the folder its listing gives, and look for files only inside this repository and your job's own folders.
