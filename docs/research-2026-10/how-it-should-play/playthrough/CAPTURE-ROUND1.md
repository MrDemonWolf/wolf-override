**Command (desktop; the phone run uses `--screen 2400x1080` and `--route=M --size=2400x1080`):**
`tools/render/render.sh --screen 1280x720 --name play-research-desktop --driver play-research/driver --timeout 3600 play-research/game/apps/game play-research/play/desktop -- --fixed-fps 60 --script res://review_capture/play.gd -- --route=D --out=/work/out --size=1280x720`

## What this is, and what it is not
- **It is scripted input, not hands-on play.** A script sent the game's own input actions (desktop) or the on-screen touch buttons' own signals (phone), and waited roughly as long as a reader needs (1.2 s plus 0.05 s per character, at most 7 s). It never moved an actor by hand, changed a game flag or skipped a beat; see "What the driver had to force" below.
- Game time is exact: with `--fixed-fps 60` every frame advances 1/60 s whatever the render speed. "t" is the time with the game running, so menus (the game pauses there) take 0 s.
- Nothing here says anything about game feel, frame rate, audio (the audio driver was Dummy) or real phone hardware.

- File names are `<route>-<n>-t<game seconds>-<what changed>.png|jpg`. A **beat** frame is taken (5 frames, 0.08 s, after the change settles; 16 frames for a knockdown) whenever anything a player would notice changes: the room, a menu or overlay, the objective card, dialogue, the context hint, the tutorial prompt, the choice or touch buttons, world state (breaker, door, safe point, traces, sentry, bolt), the coolant line, the sentry's or the tank's state, WOLF's movement target, or a knockdown. A **1-second** frame is taken whenever 1 s of game time passes with no other frame.
- Every frame has one JSON line in `desktop/_log.jsonl` and `phone/_log.jsonl`. Each line holds the game time and frame, the room, the overlay, the engineer's and WOLF's positions, the camera centre and zoom, the objective card and the current objective, the speaker and dialogue, the context hint, the tutorial prompt, any choices on screen, the buttons on screen, the end-card text, the controls held, the inputs since the previous frame, and about 30 state flags. `_run.json` holds each run's notes and the list of what was forced.
- Contact sheets show 6x6 frames per page, one set per room in the order the rooms were visited: `01-title`, `02-opening`, `03-corridor`, `04-records`, `05-junction` (3 pages, including Pause/Settings and the knockdowns), `06-endcard`, `07-title` (back at the title afterwards). Yellow captions mark beat frames and grey captions mark 1-second frames.

## What the driver had to force
- **The studio logo was skipped:** the driver instantiates `scenes/main.tscn` directly; the project's main scene is `studio_logo.tscn`. The logo is not in these frames.
- **No teleports and no state writes.** Every move was a held move action or touch button. Every interaction was USE (a tap or a hold) or a choice key or button. Menus were driven by emitting the buttons' own `pressed` signals; the settings tabs were selected by setting `tabs.current_tab`, which is what a click on a tab does.
- **The save and settings paths were set to fresh `user://play-research-*` files**, and the game's `auto_pause_on_focus_loss` was set false, so that every run starts as a New Game with default settings.
- **The phone run forced `touch_enabled = true`.** The container is Linux, so the game would otherwise show the keyboard layout. Taps are the touch buttons' own `button_down` and `button_up`, so a button that was not on screen could not be pressed; no such fallback was needed (`forced` in `phone/_run.json`).
- **The window size was forced:** the title applies its saved or default window size at launch. The phone window was set back to 2400x1080 within the first frame, and the desktop window was already 1280x720.
- **The render loop was off between captures.** The game has no GPU particles, sub-viewports or screen-reading shaders, so each saved frame is a complete render of that moment, drawn in the frame it was taken. Game logic still ran every 1/60 s. This was needed because rendering all ~12,000 frames in software ran at about 2 frames a second.
- **The phone frames were composited onto a black 2400x1080 frame.** The project uses Godot's default stretch aspect `keep`, so on a 20:9 screen the game draws its 16:9 picture (1920x1080) with 240 px black bars at each side. The viewport image was centred on black, so each frame is the whole screen as it would show it. That pillarboxing is the game's real behaviour at this aspect, not a capture artifact.
- **The DEBUG button visible on the phone frames** is the debug tools' touch button. It shows because the container runs a debug build (`OS.is_debug_build()`). A release export would not show it. It does not appear on the desktop keyboard layout.
- **The timing was chosen in advance, not reacted to.** Stopping in the blast zone and walking into the sentry's sight were deliberate mistakes. The timed drop on the desktop route waits for the sentry to turn back between x 750 and 772, which reads its live position, as a player watching it would. WOLF's bait on the phone route waits for the game's own `_bait_holding()` before DROP.

## Limits
- Scripted, not played. Read timing is a formula. No hesitation, mis-taps, overshoots or exploring are modelled beyond the two planned mistakes. These frames cannot validate game feel.
- The renders are software OpenGL in a container. Compare them only with other `render.sh` captures. They are not a Mac GPU, a phone GPU, or real phone DPI or notch/safe-area behaviour.
- No audio was captured.
- The 1-second frames are JPEG at quality 90, so judge fine pixel detail from the PNG beat frames.
- The two runs take different story branches on purpose, so desktop and phone frames of the same beat are not always the same moment.
